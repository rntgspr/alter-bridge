# T1 - Decide the agent naming contract

## What to do

Trace the current addressing and mailbox behavior through the bridge commands
and provider session stores. Gather evidence for lifecycle edge cases and
recommend one naming contract with a bounded implementation path.

## Context

`specs/bridge/index.md` describes `provider:value`, name-based mailbox slugs,
ambiguity handling, and Claude automatic names that can change on resume.
`maintenance-go-relay` T1 and T2 are implemented; its T3 still owns live relay
verification. The user reports that relay works in Claude today, which does
not settle naming stability or satisfy T3's recorded AC8.

## Implementation

1. Trace `send`, `hook`, `watchpaths`, `relay`, and `who` through
   `go/internal/session`, `go/internal/address`, and the provider stores.
2. Reproduce or mark unverified the behavior for rename, resume, duplicate
   names, archived or reused names, missing stores, and addressing by id.
3. Compare name-keyed and id-keyed mailboxes, plus any concrete third option
   justified by the evidence. Include effects on existing messages and the
   agent-facing address format.
4. Record the recommendation, rejected options, risks, affected spec claims,
   code paths, and testable criteria for a separate implementation plan in
   `handoff-t1.md`.

## Done when

- [ ] Every acceptance criterion in the plan has recorded evidence or a
  clearly labeled unverified case.
- [ ] `handoff-t1.md` states a recommended contract and actionable follow-up
  criteria without changing runtime behavior.
